A simple chidb session
=======================

This is a real, unedited transcript (build from a clean checkout, then run
the demo below) -- not a mock-up. `chidb` reads SQL statements from a file
or stdin and, for SELECT, prints one line per result row with columns
separated by "|".

    $ ./configure && make
    $ ./chidb /tmp/library.cdb < demos/library.sql

demos/library.sql contains:

    CREATE TABLE books(id INTEGER PRIMARY KEY, title TEXT, author TEXT, year INTEGER);
    INSERT INTO books VALUES(1, "The Pragmatic Programmer", "Hunt & Thomas", 1999);
    INSERT INTO books VALUES(2, "Structure and Interpretation of Computer Programs", "Abelson & Sussman", 1985);
    INSERT INTO books VALUES(3, "The C Programming Language", "Kernighan & Ritchie", 1978);
    INSERT INTO books VALUES(4, "Design Patterns", "Gamma et al.", 1994);
    SELECT * FROM books;
    SELECT title FROM books WHERE year < 1990;
    SELECT title, author FROM books WHERE id = 3;
    CREATE INDEX idxYear ON books(year);
    SELECT title FROM books WHERE year = 1994;
    SELECT title FROM books WHERE year > 1985;

And produces exactly this output (CREATE TABLE/INSERT/CREATE INDEX print
nothing -- they only run their DBM program for effect, not rows):

    1|The Pragmatic Programmer|Hunt & Thomas|1999
    2|Structure and Interpretation of Computer Programs|Abelson & Sussman|1985
    3|The C Programming Language|Kernighan & Ritchie|1978
    4|Design Patterns|Gamma et al.|1994
    Structure and Interpretation of Computer Programs
    The C Programming Language
    The C Programming Language|Kernighan & Ritchie
    Design Patterns
    Design Patterns
    The Pragmatic Programmer

/tmp/library.cdb is now a real, well-formed chidb file: page 1 is the
schema table (one row for "books", one for "idxYear"), page 2 is the
"books" table B-Tree, and page 3 is the "idxYear" index B-Tree. It can
also be queried again later, in a fresh invocation of the shell, and with
`.headers on` to label columns:

    $ ./chidb /tmp/library.cdb
    chidb> SELECT title FROM books WHERE year >= 1994;
    The Pragmatic Programmer
    Design Patterns
    chidb> .headers on
    chidb> SELECT title, year FROM books WHERE year >= 1994;
    title|year
    The Pragmatic Programmer|1999
    Design Patterns|1994

Rows come back in ascending order of the table's primary key, "id" -- 1
then 4 here, since neither query above touches `idxYear` at all (no
WHERE clause on either). The last two queries in library.sql do use it,
though, and their row order shows that: `WHERE year = 1994` is a single
row so order isn't visible, but `WHERE year > 1985` comes back "Design
Patterns" (1994) then "The Pragmatic Programmer" (1999) -- ascending by
*year*, not by "id" (which would have put "The Pragmatic Programmer",
id 1, first) -- because the index is what's actually being walked.
`chidb library.cdb` then `EXPLAIN SELECT title FROM books WHERE year >
1985;` confirms it directly: a `SeekGt` into `idxYear` followed by an
`IdxPKey`-driven `Seek` into `books`, then a plain `Next` (not
`Rewind`/`Next`) walking the index forward from that point on -- an
equality test (`year = 1994`) compiles the same way but with `Seek`
instead of `SeekGt`, and no trailing `Next` loop since there's at most
one match. `WHERE year < 1990` (the second query, run before `idxYear`
even exists) still falls back to the ordinary `Rewind`/`Next` full scan,
which is why it and `SELECT title, author FROM books WHERE id = 3`
return in "id" order above.

A two-table NATURAL JOIN
------------------------

    $ ./chidb /tmp/join.cdb < demos/join.sql

demos/join.sql:

    CREATE TABLE departments(id INTEGER PRIMARY KEY, name TEXT);
    CREATE TABLE courses(code INTEGER PRIMARY KEY, title TEXT, id INTEGER);
    INSERT INTO departments VALUES(1, "Engineering");
    INSERT INTO departments VALUES(2, "Math");
    INSERT INTO departments VALUES(3, "Physics");
    INSERT INTO courses VALUES(100, "Intro to Programming", 1);
    INSERT INTO courses VALUES(200, "Calculus", 2);
    INSERT INTO courses VALUES(300, "Orphan Course", 99);
    SELECT * FROM courses NATURAL JOIN departments;
    SELECT c.title, d.name FROM courses c NATURAL JOIN departments d WHERE d.name = "Math";

output:

    100|Intro to Programming|1|Engineering
    200|Calculus|2|Math
    Calculus|Math

`courses` and `departments` share a column name, "id" -- that's what
`NATURAL JOIN` matches on. Course 300 ("Orphan Course", id 99) has no
matching department and department 3 ("Physics") has no matching course,
so an (inner) natural join drops both; `SELECT *` shows "id" only once
(coalesced), not once per table. The second query shows a table alias
(`courses c`) with a table-qualified WHERE (`d.name = "Math"`) on the
right-hand table.

Sigma-pushing: watching the optimizer rewrite a query
------------------------------------------------------

    $ ./chidb /tmp/sigma-push.cdb < demos/sigma-push.sql

demos/sigma-push.sql:

    CREATE TABLE departments(id INTEGER PRIMARY KEY, name TEXT);
    CREATE TABLE courses(code INTEGER PRIMARY KEY, title TEXT, id INTEGER);
    INSERT INTO departments VALUES(1, "Engineering");
    INSERT INTO departments VALUES(2, "Math");
    INSERT INTO courses VALUES(100, "Intro to Programming", 1);
    INSERT INTO courses VALUES(200, "Calculus", 2);
    INSERT INTO courses VALUES(300, "Advanced Calculus", 2);
    CREATE INDEX idxCode ON courses(code);
    .opt "SELECT title FROM courses NATURAL JOIN departments WHERE courses.code > 150;"
    SELECT title FROM courses NATURAL JOIN departments WHERE courses.code > 150;

output:

    Project([title],
            Select(courses.code > int 150,
                    NaturalJoin(
                            Table(courses),
                            Table(departments)
                    )
            )
    )

    Project([title],
            NaturalJoin(
                    Select(courses.code > int 150,
                            Table(courses)
                    ),
                    Table(departments)
            )
    )
    Calculus
    Advanced Calculus

`.opt "SQL"` prints a query's parsed tree both before and after
optimization, without running it -- this is the shell command
assignment_opt.html specifies for observing "pushing sigmas" directly.
Before: the `courses.code > 150` filter sits above the whole join, as
written. After: since that condition only touches `courses`, the
optimizer has moved it down to wrap `Table(courses)` directly, so it can
be checked (and rows discarded) before ever pairing that row with
anything from `departments` -- normal `SELECT` execution (the second
statement here, not `.opt`) always goes through this same rewrite first,
not just when `.opt` is asked to show it.

`idxCode` on `courses(code)` adds one more thing to see once the
condition has been pushed down next to its own table: `chidb
sigma-push.cdb` then `EXPLAIN SELECT title FROM courses NATURAL JOIN
departments WHERE courses.code > 150;` shows a `SeekGt` into `idxCode`
for the `courses` side of the join instead of a `Rewind`/`Next` scan --
the pushed-down `Select(courses.code > int 150, Table(courses))` from
the tree above isn't just discarding non-matching rows one at a time
after fetching them, it compiles to skipping straight to the first
matching entry in the index and walking forward from there, the same
range-seek codegen the single-table case above uses.
